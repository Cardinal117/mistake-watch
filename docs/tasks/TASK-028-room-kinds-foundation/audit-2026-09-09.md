## Confirmed findings

### F1 — Shared metadata remains listed for a disabled account

Priority: **P2 — authorization consistency; fix before exposing Shared.** Task 028.4.

`app/api/account/rooms/route.ts:15` checks signed-in status, then calls the admin-backed listing. `lib/account/room-data.ts:71–78` applies an active-owner filter only to Personal; `lib/account/room-projection.ts:55` accepts Shared based on the public member ID list. A disabled Auth account can therefore still receive its Shared room metadata through the account endpoint, although room context/admission reject it.

Actual local HTTP reproduction with a synthetic account: create Shared, disable its profile, request `/api/account/rooms`, and compare authenticated `shared_room_context`:

```text
accountStatus: disabled
accountRoomsHttp: 200
sharedRoomStillListed: true
directRoomContext: null
```

This proves a metadata-listing gap, not a playback, private taste, or other-account data bypass. The synthetic account and owned room were deleted afterwards.

Required correction: enforce active eligible-account access at the shared listing boundary used by both dashboard and API, preserving Legacy semantics. Add disabled/anonymous/removed-account listing tests alongside the existing direct-room denial tests.

### F2 — Changing one consent option removes evidence for both

Priority: **P2 — independent consent behaviour.** Tasks 028.3/028.4.

Both switches share one consent epoch. `20260908131607_shared_room_membership_and_consent.sql:162–178` revokes that whole epoch whenever either flag changes. The read projection in `20260908124308_recommendation_learning_policy.sql:109–120` excludes all evidence tied to the revoked epoch.

Rolled-back database reproduction:

```text
Contribution ON, individual learning ON, one eligible choice: room count 1
Keep contribution ON, turn individual OFF: room count 0
Add a new choice while contribution remains ON: room count 1
Keep contribution ON, turn individual ON: room count 0
```

Thus even enabling the second option removes earlier room contributions. The reciprocal problem follows from the shared epoch/read filter. This is loss of eligible evidence, not unauthorized additional learning.

Required correction: preserve eligibility for the unchanged scope while revoking only the changed scope. Retain the existing guarantees that withdrawal removes the affected historical contribution and re-grant does not revive withdrawn evidence. Add a full two-toggle transition matrix, delayed ingestion, replay and removal-race coverage.

### F3 — Account Leave strands Shared membership in an inconsistent state

Priority: **P2 — membership/lifecycle correctness.** Task 028.4.

The account UI offers joined Shared members the existing Leave action (`lib/account/room-management-policy.ts:33`, `components/account/account-room-row.tsx:41`). Its confirmation says it will remove the room from the account. `lib/account/actions.ts:88–94,137–174` deletes public membership and related account rows through the admin client, but never updates `private.shared_memberships`, closes consent, or requests live revocation.

A rolled-back local SQL probe executed the same three service-role deletes for an approved non-owner:

```text
public member row: deleted
shared_room_context state: approved
revocation_pending: false
ordinary authenticated room SELECT count: 0
```

Source verification establishes the resulting split: renewed admission requires the now-missing public member (`lib/rooms/membership.ts:69–75`), while owner reapproval returns the old member ID when private state is already approved (`20260908131607_shared_room_membership_and_consent.sql:110`). The account action makes no live-revocation call. The probe did not claim a full browser click/live-session reproduction.

Required correction: distinguish normal navigation out of a room, which must preserve return membership, from permanent account Leave. For permanent Leave, use a coherent self-withdrawal transaction and the trusted live revocation/retry flow. Test account-list disappearance, reconnect, all connected devices, consent treatment and later fresh approval. If permanent Shared Leave is intentionally deferred, hide/deny this unsupported command until its semantics are implemented.

### F4 — Adding a new item with Play Next is ignored as learning evidence

Priority: **P2 — producer/consumer contract mismatch.** Task 028.3; affects Personal and opted-in Shared.

`spacetime/src/index.ts:1246–1250` emits `queue_play_next` with reason `add_as_next` when adding a new item as next. Promoting an existing queue item uses `priority_play_next`. The eligibility predicate at `20260908124308_recommendation_learning_policy.sql:47–48` only recognizes the latter pairing; its `add_as_next` allowance is attached to `queue_added` instead.

Actual ingestion RPC in a rolled-back Personal fixture:

| Event type | Reason | Account eligible | Room eligible |
| --- | --- | --- | --- |
| queue_play_next | add_as_next | false | false |
| queue_play_next | priority_play_next | true | true |

Playback/queue ordering itself is unaffected. The meaningful user choice silently fails to inform the new learning policy.

Required correction: align the allowlist with actual trusted producer combinations without treating arbitrary reorder/removal as interest. Add producer-to-ingestion coverage for both Play Next paths, consent-off cases and idempotent replay.

### F5 — Listen catalogue exclusion is not an enforced acceptance rule yet

Priority: **P2 acceptance gap**, pre-existing discovery behaviour; not introduced by the TASK-028 migrations. Cross-cutting criterion R1.

The approved rule excludes uploads from automatic Listen recommendations while retaining manual catalogue access. Existing `lib/recommendations/listen-discovery.ts:58–66,272–292,341–358` can select uploaded queue/history items for the contextual recommendation shelf. `components/room/listen/discovery/discovery-panel.tsx:165` passes the items through. The ranking request also has no mode field, and the generic hard filter checks catalogue authorization rather than Listen eligibility (`ranking-inputs.ts:160`).

A direct execution of the real shelf builder with a synthetic uploaded history item and unavailable provider returned that item under both `room-picks` and `because-listened`. Its appearance in factual Recently played is separate and need not be forbidden. This was a helper-level reproduction, not a fresh production-provider/browser test.

Required correction: explicitly enforce the no-upload rule for automatic/contextual Listen recommendations, including fallback candidates, without hiding manual queue/history/catalogue functionality. Add narrow coverage and resolve this before claiming R1 passed. Broader candidate sourcing, ranking quality and autoplay remain follow-on work.
