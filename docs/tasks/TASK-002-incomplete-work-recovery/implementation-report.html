Implementation Report

TASK-002.8I Signal State Vocabulary And Processing Status UX

Implemented locally. The media/upload UI now routes important waiting, upload, processing, approval, recoverable, failed, and ready states through a normalized display-state resolver and shared Signal primitives instead of scattered component conditionals.

Local only Resolver first No fake CloudConvert progress No deploy

What Changed

State Layer

  • Added SignalDisplayState with state, label, detail, tone, optional real progress, latest event, and actions.
  • Added resolver helpers for R2 uploads, recoverable multipart sessions, and media asset processing.
  • Added tests for direct, queued, approval, failed, recoverable, expired, and real-progress cases.

Shared Components

  • Added SignalStatusChip, SignalInlineStatus, SignalProgressBar, and SignalSkeleton.
  • Added MediaProcessingStatus, MetadataPlaceholderChips, and IdleSignalState.
  • Kept RoomTransitionOverlay as the blocking transition surface.

UI Replacements

  • Owner upload and recoverable multipart cards now consume normalized states.
  • YouTube search and metadata loading now use skeleton placeholders.
  • Awaiting-media watch stage now uses an idle state instead of a loading/progress visual.

Important Behavior

Progress Rules

  • R2 single and multipart uploads now report real transfer progress to 100%.
  • Recoverable uploads show saved byte progress from the durable session.
  • CloudConvert queued/converting/exporting states do not show fake percentages.

Recovery Rules

  • Approval-required media resolves to blocked with an owner action.
  • Failed media resolves to failed with retry-oriented copy.
  • Expired multipart sessions resolve to cleanup-oriented failed states.
